# 사내 반입 검증 체크리스트

Windows와 Mac에서 각각 확인합니다.

셸 정책은 **AI에게 셸 도구 호출을 요청하여** 확인합니다. 터미널 직접 실행이나 `!` 셸은 같은 정책 검사 경로가 아닙니다.

AI의 설명만으로 체크하지 말고 실제 도구 호출·결과와 감사 서버 기록을 확인합니다. 호출되지 않은 항목은 미실시입니다.

## 실행 및 기본 기능

- [ ] **실행 확인:** 배포 실행파일의 `--version`이 전달받은 버전과 일치하고 TUI가 정상적으로 열립니다.
- [ ] **개인정보 고지:** TUI 홈에 개인정보·민감정보 입력 주의 문구가 표시됩니다.
- [ ] **사내 모델 연결:** 새 대화에서 `QA_CHAT_OK라고 답해줘`를 요청하면 사내 모델이 응답합니다.
- [ ] **웹 실행:** `opencode web`으로 웹 화면이 열리고 사내 모델과 대화할 수 있습니다. 외부 웹 화면 다운로드가 필요하지 않습니다.
- [ ] **파일 읽기·검색:** 테스트 파일을 Read와 Grep 도구로 읽고 검색할 수 있습니다. `rg` 다운로드 또는 실행파일 없음 오류가 발생하지 않습니다.
- [ ] **파일 편집:** 아래 방법으로 수정 내용이 실제 파일에 저장되는지 확인합니다.
  - 준비: 테스트 프로젝트에 `qa-edit.txt`를 직접 만들고 첫 줄에 `alpha=1`, 둘째 줄에 `keep=this`를 입력해 저장합니다.
  - 요청: `파일 편집 도구로 qa-edit.txt의 alpha=1을 alpha=2로 바꿔줘. 나머지 내용과 다른 파일은 수정하지 마.`
  - 확인: 도구 실행이 끝나면 메모장이나 편집기로 파일을 다시 엽니다. 첫 줄만 `alpha=2`로 바뀌고 둘째 줄 `keep=this`는 유지돼야 합니다.
  - 판정: 실제 편집 도구의 성공 결과와 저장된 파일 내용을 모두 확인한 뒤 체크합니다.
- [ ] **세션 저장:** 새 대화 후 프로그램을 종료하고 다시 실행해도 대화 기록을 열 수 있습니다.

- [ ] **작업 중단·재요청:** 응답 생성과 진행 중인 셸 실행을 각각 중단한 뒤 새 요청을 처리할 수 있는지 확인합니다.
  1. 긴 설명을 요청하고 답변이 생성되는 동안 중단합니다. TUI에서는 기본 Esc를 누른 뒤 'again to interrupt' 안내가 나오면 한 번 더 누릅니다. 웹에서는 생성 중 표시되는 중단 버튼을 사용합니다. 키 설정을 바꿨다면 실제 중단 키를 사용합니다.
  2. 답변 추가 생성이 멈추고 실행 중 표시가 해제되는지 확인합니다. 이어서 `QA_AFTER_STOP이라고만 답해줘`를 보내 정상 응답을 확인합니다.

- [ ] **한글·공백 경로:** 한글과 공백이 있는 경로에서도 읽기·검색·편집이 되는지 확인합니다.
  1. 테스트 프로젝트에 `테스트 폴더`를 만들고 그 안의 `검증 파일.txt`에 `QA_PATH_OK`와 `alpha=1`을 각각 한 줄씩 저장합니다.
  2. AI에게 요청합니다: `Read로 "테스트 폴더/검증 파일.txt"를 읽고, Grep으로 테스트 폴더 안의 QA_PATH_OK를 찾아줘. 그다음 파일 편집 도구로 alpha=1만 alpha=2로 바꿔줘. 셸로 대신하지 마.`
  3. 실제 도구 결과에서 올바른 파일을 읽고 검색했는지 확인합니다. 탐색기/Finder에서 원래 파일을 다시 열어 `QA_PATH_OK`가 유지되고 `alpha=2`로 바뀌었는지, 잘못된 경로에 다른 파일이 생기지 않았는지 확인합니다. Windows와 Mac을 각각 기록합니다.

- [ ] **기록이 많은 상태의 웹 사용:** 세션 수가 많고 긴 대화가 있는 프로필로 웹 초기 로딩·세션 전환·스크롤을 확인합니다.

## 셸 및 도구 정책

Windows는 CMD/PowerShell 모두 테스트합니다. Mac은 bash/zsh 기준입니다.
각 명령은 AI에게 `셸 도구로 아래 명령을 그대로 실행해줘. 다른 명령으로 대체하지 마`라고 요청합니다.

- [ ] **bash allow 확인:** 아래 명령이 회사 승인창 없이 실행되고 테스트 폴더의 파일 목록이 나옵니다.

  | 환경 | 요청할 명령 |
  | --- | --- |
  | Windows CMD | `dir .` |
  | Windows PowerShell | `Get-ChildItem -Path .` |
  | Mac | `ls -la .` |

- [ ] **bash 승인 요청:** 테스트 프로젝트에 **빈 폴더 `qa-empty`를 직접 만든 뒤**, 아래 명령을 요청합니다. 승인창에서 선택하기 전에는 폴더가 남아 있어야 합니다.

  | 환경 | 요청할 명령 |
  | --- | --- |
  | Windows CMD | `rmdir qa-empty` |
  | Windows PowerShell | `Remove-Item -LiteralPath qa-empty` |
  | Mac | `rmdir qa-empty` |

  실제 작업 폴더 대신 준비한 빈 테스트 폴더만 대상으로 합니다. 승인 후에는 이 폴더만 삭제돼야 합니다. 반복 시험 전에 같은 빈 폴더를 다시 만듭니다.

- [ ] **bash 차단 확인:** 아래 명령은 현재 allow/ask 목록 밖이므로 정책상 거절되고 실행되지 않습니다. 명령 미설치나 문법 오류는 차단 성공이 아닙니다.

  | 환경 | 요청할 명령 |
  | --- | --- |
  | Windows CMD | `help dir` |
  | Windows PowerShell | `Get-Date -Format yyyy-MM-dd` |
  | Mac | `uname -s` |

- [ ] **승인 거절:** 위 빈 폴더 삭제 요청의 승인창을 거절하면 명령이 실행되지 않고 `qa-empty`가 남아 있습니다.
- [ ] **1회 승인·재승인:** 위 명령을 다시 요청하여 한 번 승인하면 실행되고, 다음 요청에서는 다시 승인이 필요합니다.
- [ ] **항상 허용 제한:** 회사 ask 명령에 '항상 허용'을 선택해도 이후 요청은 다시 승인해야 합니다. UI에 선택지가 없다면 서비스 회귀 테스트로 확인하고 현장 항목은 미실시로 기록합니다.
- [ ] **동시 승인 독립성:** 아래 절차로 한 요청의 승인이 다른 대기 요청을 풀지 않는지 확인합니다.
  1. 테스트 프로젝트에 빈 폴더 `qa-empty-a`와 `qa-empty-b`를 직접 만듭니다.
  2. 같은 대화에서 요청합니다: `아래 두 명령을 같은 응답에서 서로 독립된 셸 도구 호출 두 개로 동시에 요청해줘. 하나의 명령으로 합치거나 순서대로 실행하지 말고, 서브에이전트도 사용하지 마.` 다음 표에서 현재 셸에 맞는 명령 두 개를 붙입니다.

     | 환경 | 첫 번째 명령 | 두 번째 명령 |
     | --- | --- | --- |
     | Windows CMD | `rmdir qa-empty-a` | `rmdir qa-empty-b` |
     | Windows PowerShell | `Remove-Item -LiteralPath qa-empty-a` | `Remove-Item -LiteralPath qa-empty-b` |
     | Mac | `rmdir qa-empty-a` | `rmdir qa-empty-b` |

  3. **두 요청이 모두 승인 대기 중인 것을 확인한 다음**, 화면에 표시된 요청 하나만 '한 번 허용'합니다. 선택한 요청의 폴더만 삭제되고 다른 폴더는 남아 있으며, 다른 요청은 계속 승인 대기여야 합니다. 남은 요청은 거절합니다.
  4. 빈 폴더 두 개를 다시 준비하고 같은 시험을 반복하되, 이번에는 한 요청에 **'항상 허용'**을 선택합니다. 이 경우에도 선택한 폴더만 삭제되고 다른 요청은 대기를 유지해야 합니다. 남은 요청은 거절합니다.
  5. 요청 두 개·선택한 승인 방식·남아 있는 폴더가 확인되는 화면을 기록합니다. 두 폴더가 함께 삭제되거나 다른 요청이 자동 승인되면 실패입니다.

  두 요청이 순차 생성됐거나 동시 대기를 확인할 수 없으면 통과가 아니라 미실시로 기록합니다. UI에 '항상 허용'이 없다면 3번 결과와 4번 미실시를 구분하고, 해당 경로는 권한 서비스 회귀 테스트로 확인합니다.

- [ ] **결합 명령 차단:** 아래 명령을 요청하면 금지 명령을 포함한 호출 전체가 차단됩니다. `QA_COMPOUND_OK`가 실제 명령 출력으로 나오면 안 됩니다.

  | 환경 | 요청할 명령 |
  | --- | --- |
  | Windows CMD | `echo QA_COMPOUND_OK && help dir` |
  | Windows PowerShell | `Write-Output QA_COMPOUND_OK; Get-Date -Format yyyy-MM-dd` |
  | Mac | `echo QA_COMPOUND_OK && uname -s` |

- [ ] **사용자 설정으로 완화 불가:** 아래 절차로 사용자 설정이 사내 승인·차단 정책을 풀지 않는지 확인합니다.
  1. 테스트 프로젝트의 `opencode.json`이 있으면 원본을 별도 복사해 둡니다. 파일이 없었다면 테스트 후 새로 만든 파일을 삭제합니다. 실제 모델·인증 설정은 그대로 유지합니다.
  2. 기존 JSON의 `permission` 항목에 `"bash": "allow"`를 병합합니다. 이미 같은 키가 있으면 값만 바꾸고 중복 키를 만들지 않습니다. `permission`이 문자열이면 백업 후 아래 객체로 임시 교체합니다. 파일 전체를 덮어쓰지 않습니다.

     ```json
     {
       "permission": {
         "bash": "allow"
       }
     }
     ```

  3. 테스트 OpenCode를 종료하고 **해당 프로젝트 폴더에서** 같은 사내 실행파일·런처로 다시 실행합니다. 새 대화를 시작합니다. 프로젝트 설정 읽기를 비활성화했거나 에이전트별 셸 권한이 덮어쓰는 환경이면, 실제 적용 설정을 먼저 확인해야 하며 확인하지 못하면 미실시로 기록합니다.
  4. 빈 폴더 `qa-empty`를 직접 만든 뒤 아래 승인 대상 명령을 AI에게 셸 도구로 요청합니다. `allow` 설정에도 **승인창이 표시돼야** 합니다. 승인하지 않고 거절하여 폴더가 남는지 확인합니다.
  5. 아래 금지 명령도 같은 대화에서 요청합니다. 승인으로 풀리거나 실행되면 안 되고 **정책상 거절돼야** 합니다.

     | 환경 | 승인 대상 명령 | 금지 명령 |
     | --- | --- | --- |
     | Windows CMD | `rmdir qa-empty` | `help dir` |
     | Windows PowerShell | `Remove-Item -LiteralPath qa-empty` | `Get-Date -Format yyyy-MM-dd` |
     | Mac | `rmdir qa-empty` | `uname -s` |

  6. 성공·실패 여부와 관계없이 테스트 OpenCode를 종료하고 원본 설정을 복원합니다. 새로 만든 설정 파일이면 삭제합니다. 다시 실행해 정상 연결되는지 확인하고, 테스트 폴더를 정리합니다.

  승인창과 정책 거절 결과를 각각 기록합니다. 설정 오류·명령 미설치·AI의 호출 생략은 정책 검증 통과로 처리하지 않습니다.

- [ ] **WebFetch 승인:** 접근이 허용된 사내 테스트 URL을 webfetch로 요청하면 승인창이 뜨고, 거절 시 접근하지 않습니다. 사용자 설정으로 도구를 숨긴 경우 실행 차단 검증은 미실시입니다.

## 감사 로그

- [ ] **입력·응답 기록:** 감사 서버에서 `QA_CHAT_OK`가 포함된 사용자 입력과 완료된 모델 응답을 확인합니다. `assistant.message`에 prompt와 response가 함께 있습니다.
- [ ] **도구 기록:** 성공한 도구의 요청·결과와 실제 승인 요청·응답이 기록됩니다. 실패·거절된 도구에는 성공 결과 이벤트가 없을 수 있습니다.
- [ ] **로그 연결:** sessionID로 대화, callID로 도구 요청·결과, requestID로 승인 요청·응답을 연결할 수 있습니다.
- [ ] **식별자·시간:** user_id는 테스트 PC의 로컬 IPv4이고 ts는 KST입니다. command는 JSON 문자열입니다.
- [ ] **감사 장애·복구(hosts 파일):** 실제 감사 서버는 중지하지 않고 **테스트 PC에서만 감사 서버 도메인을 루프백 주소로 바꿔** 접속 실패를 만듭니다.
  1. 정상 상태에서 테스트 문장을 보내 모델 응답과 감사 수신이 모두 되는지 먼저 확인합니다. 빌드에 들어간 감사 URL의 **호스트명만** 담당자에게 확인합니다. 예시 `audit.example.invalid`는 실제 값이 아니므로 테스트할 때 실제 호스트명으로 바꿉니다. URL의 `https://`, 포트, 경로는 hosts에 적지 않습니다.
  2. 테스트 OpenCode를 모두 종료합니다. 관리자 권한으로 아래 hosts 파일을 열기 전에 원본을 별도 백업합니다. 기존에 같은 호스트명이 있으면 해당 줄도 기록하고, 테스트 동안 기존 매핑과 중복되지 않게 임시 변경합니다. 다른 도메인 줄은 유지합니다.

     | 환경 | hosts 파일 | 편집 방법 |
     | --- | --- | --- |
     | Windows | `%SystemRoot%\System32\drivers\etc\hosts` | 메모장을 관리자 권한으로 열고 파일 형식을 '모든 파일'로 선택합니다. 확장자 없이 `hosts`로 저장합니다. |
     | Mac | `/etc/hosts` | 터미널에서 `sudo nano /etc/hosts`로 엽니다. 저장은 Ctrl+O, Enter, 종료는 Ctrl+X입니다. |

  3. hosts에 아래처럼 IPv4·IPv6 매핑을 넣습니다. 테스트 PC에서 감사 URL과 같은 포트에 로컬 서버가 실행 중이지 않아야 접속 실패를 확실히 만들 수 있습니다.

     ```text
     127.0.0.1 audit.example.invalid
     ::1       audit.example.invalid
     ```

  4. 관리자 터미널에서 아래 캐시 갱신 명령을 실행하고, 조회 결과가 `127.0.0.1` 또는 `::1`인지 확인합니다. 이 준비 명령들은 OpenCode의 AI 셸 도구가 아니라 사용자가 OS 터미널에서 실행합니다.

     | 환경 | 캐시 갱신 | 매핑 확인(예시 도메인을 교체) |
     | --- | --- | --- |
     | Windows | `ipconfig /flushdns` | `ping -n 1 audit.example.invalid` 출력의 대상 주소 확인. ping 성공 여부는 감사 전송 성공 여부가 아닙니다. |
     | Mac | `sudo dscacheutil -flushcache` | `dscacheutil -q host -a name audit.example.invalid` |

  5. 같은 사내 실행파일·런처로 OpenCode를 다시 열어 새 대화에서 `QA_AUDIT_BLOCK이라고 답하고, 셸 도구로 echo QA_AUDIT_TOOL을 실행해줘`라고 요청합니다. 감사 전송 오류가 표시되고 해당 요청의 모델 호출·도구 실행이 진행되지 않아야 합니다. 화면이 멈춘 것만으로 판정하지 말고, 가능하면 모델 서버에서 해당 요청이 수신되지 않았는지도 확인합니다. 프로그램 자체가 종료돼야 한다는 뜻은 아닙니다.
  6. 성공·실패 여부와 관계없이 테스트 OpenCode를 종료하고 **hosts에서 바꾼 항목을 원래대로 복원**합니다. 백업 이후 다른 수정이 없을 때만 파일 전체를 백업본으로 되돌립니다. 같은 캐시 갱신 명령을 실행하고 원래 감사 서버 주소로 해석되는지 확인합니다.
  7. OpenCode를 다시 열어 **새 요청**을 보냅니다. 모델 응답·도구 실행과 감사 서버 수신이 다시 정상이어야 합니다. 실패했던 요청의 자동 재실행을 기대하지 않습니다.

  감사 URL이 IP 주소 자체이거나 모델 서버와 같은 호스트명이면 이 방법으로 감사 연결만 분리할 수 없습니다. 프록시가 도메인을 대신 해석하는 환경에서도 hosts가 적용되지 않을 수 있습니다. 모델 연결까지 막혔거나 감사 연결 실패를 확인하지 못한 경우 미실시로 기록하고, 담당자에게 테스트 PC의 감사 목적지·포트만 차단하는 방법을 요청합니다.
  실제 호스트명과 테스트 증빙은 사내에만 보관합니다. Windows 명령 참고: [Microsoft ipconfig 문서](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ipconfig). Mac 명령은 OS의 `man dscacheutil`에서 확인할 수 있습니다.

## 서브에이전트

- [ ] **기본 동작:** `내장 task 도구로 general 서브에이전트를 호출해 테스트 파일을 요약해줘`를 요청하면 실제 자식 세션이 생성되고 결과가 부모에게 반환됩니다.
- [ ] **자식 세션 확인:** 아래 절차로 실제 자식 대화와 도구 결과를 확인합니다.
  1. 테스트 프로젝트에 `qa-child.txt`를 직접 만들고 `QA_CHILD_OK`를 입력해 저장합니다.
  2. 부모 대화에서 요청합니다: `내장 task 도구로 general 서브에이전트 하나를 호출해줘. 자식이 Read 도구로 qa-child.txt를 직접 읽고 내용을 보고하게 해줘. 부모가 대신 읽지 말고 파일은 수정하지 마.`
  3. TUI에서 해당 task/서브에이전트 실행 항목을 클릭해 자식 대화로 이동합니다. 마우스 이동이 안 되면 화면의 'view subagents' 안내에 표시된 자식 이동 단축키를 사용합니다. 단축키는 사용자 설정에 따라 다를 수 있습니다.
  4. 자식 대화에 전달된 작업 지시, `qa-child.txt`에 대한 실제 Read 호출과 결과 `QA_CHILD_OK`, 자식의 답변이 보이는지 확인합니다. 부모의 '서브에이전트가 읽었다'라는 설명만 있으면 통과가 아닙니다.
  5. 자식 화면의 부모 이동 안내를 사용해 원래 대화로 돌아옵니다. 부모 대화에도 자식의 완료 결과가 전달됐는지 확인합니다. 기본 TUI 부모 이동 키는 위쪽 화살표이며, 사용자 설정을 바꿨다면 해당 키를 사용합니다.

  자식 대화가 열리지 않거나 작업·도구 결과를 확인할 수 없으면 실패 또는 미실시 이유를 기록합니다. 자식의 Read 결과 화면과 부모의 결과 수신 화면을 증빙으로 남깁니다.

- [ ] **정책 적용:** 자식의 실제 셸 호출도 사내 금지 정책으로 차단되는지 확인합니다.
  1. 부모 대화에서 요청합니다: `내장 task 도구로 general 서브에이전트 하나를 호출해줘. 자식에게 아래 명령을 셸 도구로 한 번만 실행하도록 전달해줘. 부모가 대신 실행하지 말고, 다른 명령이나 셸로 대체하지 마. 정책상 거절되면 재시도하지 말고 결과만 보고해줘.` 다음 표에서 실제 셸에 맞는 명령을 붙입니다.

     | 환경 | 자식에게 요청할 금지 명령 |
     | --- | --- |
     | Windows CMD | `help dir` |
     | Windows PowerShell | `Get-Date -Format yyyy-MM-dd` |
     | Mac | `uname -s` |

  2. 부모의 task 실행 항목에서 해당 자식 세션을 엽니다. 자식이 셸 도구에 전달한 명령이 요청한 것과 같은지 확인합니다.
  3. 자식의 도구 결과가 **사내 권한 정책에 따른 거절**인지 확인합니다. 명령 실행 결과가 나오거나 승인을 통해 실행할 수 있으면 실패입니다. 명령 미설치·문법 오류는 차단 성공이 아닙니다.
  4. 부모로 돌아와 자식의 차단 결과가 전달됐는지 확인하고, 자식의 명령 입력과 거절 결과 화면을 기록합니다.

  자식이 도구를 호출하지 않고 말로만 거절했거나 부모가 대신 호출했다면 이 검사는 미실시입니다. 정상적인 정책 거절을 '서브에이전트 실행 불량'으로 기록하지 않습니다.

- [ ] **감사 기록:** 내장 task 자식의 지시·답변·도구 기록이 실제 감사 서버에 수신·저장되는지 확인합니다.
  1. 앞의 자식 세션 시험에서 사용한 `qa-child.txt`와 `QA_CHILD_OK`, 실행 시각으로 감사 서버 로그를 조회합니다.
  2. 부모의 task 결과·도구 메타데이터에 있는 자식 세션 ID와 감사 로그의 `sessionID`를 대조합니다. 자식 ID를 확인할 수 없으면 미실시 사유를 적습니다.
  3. 자식 ID로 `user.message`, 완료된 `assistant.message`, 성공한 Read의 `tool.call.request`와 `tool.call.output`을 확인합니다. 부모의 task 호출 기록만 있는 것으로 통과 처리하지 않습니다.

  현재 코드는 내장 task 자식도 감사 전송 경로를 거칩니다. 이것은 실제 서버 수신·저장 완료를 뜻하지 않으므로 현장에서 확인합니다. 외부 플러그인의 서브에이전트는 별도 검사합니다.

- [ ] **백그라운드 동작(사용 시):** 자식 작업이 진행되는 동안 부모 대화를 계속할 수 있고 완료 결과가 자동으로 돌아오는지 확인합니다.
  1. 테스트 프로젝트의 `qa-background` 폴더에 민감정보가 없는 텍스트 파일을 여러 개 준비합니다. 자식이 각 파일을 읽고 요약할 수 있는 분량으로 준비하며, 파일을 바꾸거나 외부에 접속하는 작업은 맡기지 않습니다.
  2. 테스트 OpenCode를 종료하고 새 터미널을 엽니다. 아래에서 실제 셸에 맞는 환경변수 설정 명령을 실행합니다. 시스템 전체 환경변수를 영구 변경하는 명령은 아닙니다.

     | 환경 | 같은 터미널에서 먼저 실행 |
     | --- | --- |
     | Windows CMD | `set "OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true"` |
     | Windows PowerShell | `$env:OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS = "true"` |
     | Mac bash/zsh | `export OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true` |

  3. **방금 설정한 같은 터미널에서** 평소 사용하는 사내 실행 명령·런처로 테스트 프로젝트를 엽니다. 예를 들어 배포 폴더에 런처가 있다면 Windows는 `.\start.cmd "C:\테스트폴더"`, Mac은 `./start.command "/테스트폴더"`입니다. 경로는 실제 테스트 폴더로 바꾸며, 원래 쓰던 모델 설정과 데이터 프로필을 유지합니다. 탐색기에서 별도로 더블클릭하면 위 터미널의 환경변수를 이어받지 못합니다.
  4. 부모 대화에 요청합니다: `내장 task 도구로 general 서브에이전트 하나를 background=true로 실행해줘. 자식은 qa-background 폴더의 각 텍스트 파일을 Read로 읽고 파일별 요약과 전체 요약을 작성해줘. 파일 수정과 외부 접속은 하지 마. 부모는 같은 작업을 대신 하지 말고, 백그라운드 작업을 시작한 직후 시작했다고만 알려줘.`
  5. 실제 task 호출의 입력·메타데이터에 `background=true`가 있거나 결과에 `Background task started` 등 백그라운드 시작 상태가 표시되는지 확인합니다. AI가 말로만 '백그라운드'라고 답한 것으로 통과 처리하지 않습니다. 활성화 환경변수 오류가 나오면 런처가 값을 덮어쓰지 않는지와 실제 실행한 프로세스를 확인합니다.
  6. 자식 작업이 아직 진행 중일 때 **부모 대화에** `QA_PARENT_OK라고만 답해줘. 자식 작업은 취소하지 마`를 보냅니다. 자식이 완료되기 전에 부모가 응답할 수 있어야 합니다. 자식 작업이 너무 빨리 끝났다면 파일 수·분량을 늘려 다시 확인하고, 이 부분을 확인하지 못하면 미실시로 적습니다.
  7. OpenCode를 계속 켜둔 채 기다립니다. 반복 조회나 sleep 명령을 AI에게 시키지 않습니다. 자식이 끝나면 부모 대화에 완료 결과가 자동 전달되고, 자식 세션에서 실제 파일 읽기·요약 결과를 확인할 수 있어야 합니다. 소리나 OS 알림만을 통과 기준으로 삼지 않습니다.
  8. 백그라운드 시작 결과, 완료 전 부모 응답, 자식 결과와 부모의 완료 수신 화면을 기록합니다. 시험이 끝나면 테스트 OpenCode와 새로 연 터미널을 종료합니다. 기존 런처·설정 파일은 변경하지 않습니다.

  이 항목은 내장 task 기능 기준입니다. 외부 플러그인의 백그라운드 작업이나 OpenCode 종료 후에도 작업이 지속되는지까지 보장하는 검사는 아닙니다.

## OMO (oh-my-openagent)

내장 task 시험과 별도로, 사내에 설치한 OMO 버전에서 확인합니다.

- [ ] **에이전트 전부 사내 모델 호출:** 활성 에이전트마다 아래 절차를 반복합니다. 대표 에이전트 하나만 성공한 것으로 전체 통과 처리하지 않습니다.
  1. 테스트 프로젝트에 `qa-omo.txt`를 만들고 `QA_OMO_FILE_OK`를 저장합니다. 에이전트별 요청에는 `QA_OMO_<에이전트명>_<시험번호>`처럼 구분 가능한 표식을 붙입니다.
  2. 해당 버전이 지원하는 에이전트 선택·위임 방식으로 실제 에이전트를 호출합니다. 파일 읽기 역할에는 `qa-omo.txt를 직접 읽고 내용을 보고해줘. 수정이나 외부 접속은 하지 마`를 요청합니다. 계획·검토 전용 역할에는 짧은 테스트 계획 작성·검토처럼 권한에 맞는 작업을 줍니다.
  3. 실제 호출 도구, 에이전트 이름, 부모/자식 세션 ID, 완료 결과를 확인합니다. 부모가 대신 처리하거나 말로만 위임한 경우는 미실시입니다. 주 에이전트는 해당 대화의 실제 선택 상태를 확인합니다.
  4. 해당 세션의 실제 `providerID`/`modelID`와 **사내 모델 서버 또는 게이트웨이의 요청 시각·요청 ID·모델명**을 대조합니다. 모델 별칭을 쓰면 서버가 실제로 연결한 모델까지 확인합니다. AI가 '사내 모델을 썼다'고 답하거나 감사 서버에 대화가 찍힌 것만으로는 통과가 아닙니다.
  5. 사용 중인 category 경유 호출과 백그라운드 위임도 같은 방법으로 확인합니다. 자식의 완료 결과가 부모에게 돌아오고, 자식 ID 기준 감사 서버에 지시·응답·실제 도구 기록이 남는지 확인합니다.

  활성 에이전트와 사용 경로마다 아래 표에 행을 추가하여 사내 시험 기록에 보관합니다.

  | 에이전트 / 호출 경로 | 예상 provider/model | 실제 provider/model | 세션 ID / 시각 | 모델 서버 요청 ID | 결과 |
  | --- | --- | --- | --- | --- | --- |
  | 주 에이전트 | 기입 | 기입 | 기입 | 기입 | 통과/실패/미실시 |
  | 활성 서브에이전트 각각 | 기입 | 기입 | 기입 | 기입 | 통과/실패/미실시 |
  | 사용 category / 백그라운드 | 기입 | 기입 | 기입 | 기입 | 통과/실패/미실시 |
  | 압축 요약 모델 | 기입 | 기입 | 기입 | 기입 | 통과/실패/미실시 |

- [ ] **기본값·fallback 확인:** 명시하지 않은 에이전트나 category가 외부 모델 기본값을 상속하지 않는지 확인합니다. fallback을 사용하는 경우 테스트 환경에서 주 모델의 일시 오류를 재현해 다음 호출도 사내 모델로 가는지 확인합니다. 외부 호출을 시도했다가 사내망에서 막힌 경우는 통과가 아닙니다. fallback 미사용은 해당없음으로 기록합니다.
- [ ] **한도 도달 전 자동 압축:** 다음 순서로 실제 자동 실행을 확인합니다.
  1. 새 테스트 대화 첫 부분에 `테스트 목표는 파일 목록 검토이며 파일 수정은 금지. 기억할 표식은 QA_OMO_KEEP_42. 1단계 목록 확인은 완료, 2단계 요약 검토는 미완료`를 입력합니다.
  2. 민감정보 없는 테스트 문서를 여러 차례 읽거나 요약하게 하여 컨텍스트 사용량을 늘립니다. 설치 버전이 임계값 조정을 지원하면 별도 테스트 설정에서만 낮춰 시험하고 종료 후 복원합니다. 고정된 임계값을 추측해서 설정하지 않습니다.
  3. 설정한 임계값 부근에서 컨텍스트 초과 오류가 나기 **전에** OMO 압축 시작 기록과 요약 완료 기록이 생기는지 확인합니다. 수동 `/compact` 실행이나 오래된 도구 출력 삭제만으로 통과 처리하지 않습니다.
  4. 압축 요약 요청도 사내 모델 서버에 도착했는지 확인하고 실제 모델·시각·요청 ID를 위 표에 적습니다. 화면 알림만으로 성공을 판정하지 않습니다.
  5. 압축 다음 모델 요청에서 입력 컨텍스트가 줄거나 여유가 회복됐는지 실제 토큰 사용량으로 확인합니다. 화면에 과거 대화가 남아 있는지는 판정 기준이 아닙니다.
